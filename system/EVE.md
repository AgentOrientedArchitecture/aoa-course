The [EVE and AGNTCY architecture reference](../course/sessions/session-03-eve/ADOPTION.md) explains the external components, actual EVE invocation, portable discovery record, local contract and evidence at each boundary. This page gives the runtime and filesystem detail.

> Protocol scope: the course bridge currently emits the A2A v0.3 JSON-RPC
> card/message shape. It demonstrates the outward boundary and registry
> integration; it is not an A2A v1 conformance implementation.

Read [`ARCHITECTURE.md`](ARCHITECTURE.md) and [`AGENTS.md`](AGENTS.md) first. This
document explains the canonical Session 3 flow: author and accept an agent
natively with [Vercel EVE](https://github.com/vercel/eve), then adopt that same
agent into AOA without moving its implementation into the AOA runtime.

## Why EVE fits AOA

EVE and AOA cover different responsibilities:

| EVE owns | AOA adds at adoption |
|---|---|
| `agent/agent.ts` model wiring | capability publication |
| `agent/instructions.md` behaviour | stable governed Agent ID |
| native CLI, runtime, sessions, and development UI | registry lifecycle and discovery |
| native acceptance of the standalone agent | outward A2A surface and estate trace boundary |

EVE does not need to know about the AOA registry or planner. AOA does not need to
know how EVE implements a session. The capability card is the adoption boundary
between them.

## Filesystem ownership

Session 3 keeps reusable runtime infrastructure separate from learner work:

```text
system/agents-eve/
  runtime/                 # course-owned image, generic bridge, and adoption assets
  workshop/                # learner-owned, bind-mounted authored workspace
    agent/
      agent.ts
      instructions.md
      channels/eve.ts
    capability-card.yaml   # generated by adoption when missing
```

The learner starts with a blank authored surface under `workshop/`: the pinned
package shell exists, but no agent files do. `eve init .` creates the agent files
there. Infrastructure is described and maintained under `runtime/`; it is not a
second agent for the learner to copy or compare against.

## The canonical build-then-adopt flow

Three commands organise the core Session 3 sequence. Use the `.sh` variants on
macOS/Linux and `.bat` variants in Windows Command Prompt from the repository
root; the walkthrough supplies the exact commands:

1. `session3-build` pre-builds the complete Session 3 image set, including
   `aoa-course/eve-workshop:0.17.1`. It starts nothing and authors nothing.
2. `session3-up` opens the native EVE workshop only. It does not start the AOA
   registry, planner, studio, or bridge.
3. `session3-adopt` creates `workshop/capability-card.yaml` automatically when
   needed, starts AOA, starts the generic bridge, and publishes the learner's
   accepted agent. It also starts AGNTCY Directory and waits for publication
   of the running AUs. The `directory` helper supports inspection and the
   discovery outage exercise later in the same walkthrough.

Inside the native workshop, the learner runs the EVE commands directly:

```sh
eve init .
eve info
eve dev
```

The learner replaces the generated model wiring with the provider-neutral
OpenAI-compatible `agent.ts` and replaces the default prompt with the bounded
`instructions.md` embedded in the
[Session 3 walkthrough](../course/sessions/session-03-eve/WALKTHROUGH.md). That contract requires
exactly five concise questions, strict word limits, JSON only, and a response no
larger than 1,200 tokens.

Native acceptance tests happen before adoption. The learner tests output shape,
lengths, grounding, and hiring-decision boundaries in `eve dev`. At that point
there is still no AOA Agent ID or registry entry.

## Provider-neutral model access

The workshop's `agent.ts` uses `createOpenAI` with environment-driven
`LLM_BASE_URL`, `LLM_API_KEY`, and `MODEL`. If no explicit base URL is set,
it derives Ollama's OpenAI-compatible `/v1` endpoint from `OLLAMA_HOST`.
`MODEL_CONTEXT_WINDOW_TOKENS` supplies metadata EVE cannot infer for local or
unlisted model IDs.

In the course `.env`, use `LLM_BASE_URL` and `LLM_API_KEY` for generation.
Compose passes those same names into EVE. Replace the key when changing endpoints.
For an unauthenticated local server use a placeholder such as `local-no-auth`.
`DECISION_API_KEY` configures the separate decision service and is not passed
to EVE as its generation credential.

This keeps provider selection in the course environment (`.env`): the authored
agent uses the OpenAI-compatible SDK without hard-coding a hosted service.
Configuration compatibility is not a claim of acceptance testing for every
provider and model. Run the native tests against the selected combination.

## Adoption into the CV workflow

Adoption gives the accepted EVE agent the `interviewer-questions` capability:

```text
parse-cv → evaluate-cv-fit → interviewer-questions
```

The generated capability card declares the evaluation and optional CV inputs,
the structured questions and Markdown outputs, constraints, evaluation signals,
and model provenance. The generic bridge stamps runtime identity and
`skills_hash`, registers the card, exposes the A2A surface, and emits trace
events.

The planner therefore treats the final step like any other AU. It retrieves
its OASF record through AGNTCY, checks the current local approved contract and
runtime binding, and invokes the A2A endpoint. It does not import EVE or depend
on EVE's session model. The course opens an EVE session per invocation; this
exercise does not demonstrate interview memory across separate requests.

The generic bridge checks JSON shape and required output fields. The native
and adopted acceptance checks must still inspect question count, word limits,
grounding and hiring-decision boundaries. Published constraints alone do not
prove that an answer meets them.

## Change lifecycle

Keep the two validation boundaries distinct:

- Changes to `agent.ts` or `instructions.md` must pass the native acceptance
  tests in `eve dev` again.
- Changes to `workshop/capability-card.yaml` require rerunning `session3-adopt`
  so the adopted runtime revalidates and republishes the contract.
- After returning to native development, rerun `session3-adopt` before AOA
  acceptance so the composed system uses the newly accepted learner files.

The complete learner sequence, copy-ready provider-neutral `agent.ts`, full
concise `instructions.md`, acceptance input, and Studio checkpoint are in the
